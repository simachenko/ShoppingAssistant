# Quickstart: Store Info RAG

This guide proves the feature works end-to-end locally, on top of an already-running
`001-smart-product-advisor` environment. It does not contain implementation code — see
`tasks.md` (generated by `/speckit-tasks`) for build-out steps, and `data-model.md` /
`contracts/` for the shapes referenced below.

## Prerequisites

- Everything in `specs/001-smart-product-advisor/quickstart.md`'s Prerequisites (this feature
  adds no new external account/service dependency).
- `LLM_PROVIDER_EMBEDDING_MODEL` — the embedding model name for the same OpenAI-compatible
  provider already configured (research.md §7), set alongside the existing
  `LLM_PROVIDER_*` variables.
- Seed data: the small `StoreDocument`/`DocumentChunk` fixture set described in research.md §12
  (delivery, payment, returns, warranty, loyalty, contacts — at least one document each), applied
  automatically the same way Catalog/Pricing demo data already is.

## Run

Same two options as `001-smart-product-advisor/quickstart.md` (Aspire primary, Docker Compose
CI-parity fallback) — no new run command. Aspire's Postgres resource migration step now also
applies the `vector` extension and the `StoreDocument`/`DocumentChunk` schema (research.md §6) as
part of the same `advisor` schema migration already run for `ConversationSession`.

## Validation Scenario 1 — Grounded answer with citation (US1, SC-001, SC-002, SC-003)

1. Open the Blazor app and start a new chat (sign in with Google, as required by
   `001-smart-product-advisor` FR-030).
2. Send: `How long does delivery take?`
3. **Expect**: an `answer` response (`contracts/advisor-conversation-api-additions.md`) whose
   `message` states a delivery timeframe, and whose `citations` array contains exactly one entry
   naming the seeded "Delivery Terms" document. No detail in `message` (a number, a condition) is
   absent from the seeded document's content.

## Validation Scenario 2 — Honest "not found" (US2, SC-004)

1. In the same or a new chat, send a question about a policy area deliberately **not** seeded
   (e.g., ask about a "price-match guarantee" when no such document exists).
2. **Expect**: an `answer` response whose `message` plainly states the information could not be
   found in the store's reference material, with an empty `citations` array — never a fabricated
   policy detail, never a citation to an unrelated seeded document.

## Validation Scenario 3 — Store/type scoping and multi-area answer (US1, US3, SC-002, SC-003)

1. Send a question naming two policy areas in one turn, each covered by a different seeded
   document type (e.g., `What payment methods do you accept, and what's your return window?`).
2. **Expect**: `message` addresses both parts, and `citations` contains an entry for each
   distinct contributing document (payment + returns) — every claim in `message` still traces to
   one of them.
3. Ask a question clearly scoped to one type (e.g., a warranty question) while loyalty-program
   content also exists in the seeded set.
4. **Expect**: `citations` names only the warranty document — no unrelated document type is
   cited.

## Validation Scenario 4 — Product questions are unaffected (FR-005, SC-007)

1. Send a product question the existing `001-smart-product-advisor` scenarios already cover
   (e.g., `What's the price of the [seeded product name]?`).
2. **Expect**: identical behavior to `001-smart-product-advisor/quickstart.md`'s own product-fact
   scenario — the response has no `citations` field, and (if request/response logging is
   inspected, e.g. via the Aspire dashboard) no call to `retrieve_store_info` appears in that
   turn's trace.

## Validation Scenario 5 — Superseded document exclusion (data-model.md `StoreDocument.Status`)

1. Using a direct database update (or a seed-data variant) mark the "Delivery Terms" document
   `Superseded` and insert a new `Active` version with different content, linked via
   `SupersedesDocumentId`.
2. Repeat Scenario 1's question.
3. **Expect**: `message`/`citations` reflect only the new `Active` version's content — the
   `Superseded` document is never surfaced as a source, and no conflict/discrepancy is reported to
   the user (research.md §6/§8's mandatory `Status = 'Active'` filter resolves this
   deterministically before ranking ever runs).
